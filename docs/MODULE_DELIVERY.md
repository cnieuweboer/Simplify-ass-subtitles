# Extensible implementation delivery — v214

This distribution release removes the active fixed module lists from the Windows
installer and updater. `simplify_ass.py`, `_simplify_ass/` and
`simplify_subtitles.py` are unchanged; the engine version remains
`2026.10.16.213`. No converter extraction or policy change is included.

## Delivery contract

The installer discovers all portable Python source paths recursively beneath
`_simplify_ass/` in its source checkout. The updater selects those same paths from
a complete, pinned GitHub tree, retaining the existing size limit, Git-blob hash
verification and Python syntax checks before running the downloaded installer.
The package initializer is required; individual implementation filenames are not
required by the delivery code. Non-source data and generated caches are excluded.
A complete source checkout remains the installer input; this does not introduce
a resolver for Python imports or runtime data dependencies.

The installer owns copying, retirement and rollback. Settings schema 2 stores
`launchers` plus an `engine_modules` list of package-relative source paths. Its
previous inventory identifies retired modules; their sources and matching
`__pycache__` files are backed up and removed in the same transaction as new
sources and settings. Nested directory creation is tracked for rollback. Empty
owned directories are tidied after commit; a locked empty directory may remain
without invalidating an otherwise successful update.

Uninstall uses the inventory, never a scan of installed Python files. Unrelated
sources, media, caches and nonempty directories survive. An incoming new module
cannot silently overwrite an unowned file. Inventory paths are validated before
use; traversal, Windows device/stream names, cache paths and case collisions are
rejected. Managed filesystem paths cannot traverse symlinks or reparse points,
including Windows junctions. Case-only module renames require a distinct portable
name instead. Corrupt settings stop installation/removal before changes rather
than discarding ownership information.

The two known v213 package paths remain only as a migration fallback for version
1 settings or installations without settings. That list is historical ownership,
not the delivery inventory, and must not grow with future extractions.

The small portable module-path predicate deliberately exists in both standalone
scripts: an old installed updater must select and verify files before it loads
the new installer. Importing the installed engine/package to share that code
would cross the bootstrap boundary. Contract checks exercise both predicates;
no new shared runtime dependency is introduced.

## Older clients

The unchanged two-module runtime lets the actual v213 updater install v214.
Afterward, its replacement discovers future modules automatically. An updater
that never installed this preparation still has its old selection rules; it
cannot download later additions. Pre-v213 clients have the same issue with the
whole private package. They must use the complete current repository installer
with `--keep-launchers`, as described in the
[Windows installation guide](../installer/windows/README.md#upgrading-older-installations).
That route also repairs an incomplete runtime left by an old updater. There is
no hidden engine import fallback or second network download inside the installer.
Keep a valid settings file with the installation so future retirement/uninstall
can identify its owned files.

## Validation

Run from the repository root with the prepared dependencies:

```sh
python tests/check_windows_installer.py
python tests/check_windows_updater.py
python validation/run_backend_check.py --backend windows tests/check_font_module.py
```

Fresh results:

- Installer: **32 passed, two native-Windows checks skipped** (34 total).
- Updater: **10 passed, one native-Windows check skipped** (11 total).
- Actual installed-engine/module checks: **five passed**, including font lookup
  and conversion from an unrelated working directory without the checkout on
  the import path, then removal of generated bytecode.
- A separate compatibility run used unchanged installer/updater sources from
  commit `465663d1b38eb03c60bddf95d60145e98dcf4c6b`: install with v213, update
  through the actual v213 downloader to v214, then use the installed new updater
  to add a nested dependency and retire the former module. The delivered engine
  imported that new dependency successfully; launcher choices and user files
  survived both updates.
- The font/MKV extraction, conversion, remux/extraction and font-sync smoke check
  passed with source files preserved.
- Complete runtime source hashes before/after are identical, including the
  private package. No engine or production batch-wrapper source changed.

Coverage includes module additions and removals without delivery-list edits,
source/cache/settings restoration after retirement fails, removal of newly
created nested directories on rollback, staging failure, recovery copies after
rollback failure, hash/syntax rejection of new modules, corrupt ownership,
unowned collisions, linked paths, launcher preferences and uninstall. Network
responses in updater tests are mocked pinned trees with real blob verification;
the tests do not depend on a moving GitHub branch.

Private migration snapshots and verification are retained under
`validation/module-delivery-v214/`. The 91-script renderer regression suite and
13-track corpus were not rerun for this distribution-only release: every runtime
source remains byte-identical to the validated v213 implementation. Earlier
results remain historical evidence, not newly claimed runs. Native Windows CMD,
self-update and NTFS validation still require a Windows host.

## After-release evaluation

Module discovery, installed ownership and transaction handling now have explicit
roles. Retired files do not require an engine workaround or a late cleanup pass.
The only retained fixed module list is the bounded legacy migration inventory;
the intentionally duplicated path validator serves two independent bootstrap
entry points. Neither needs a dedicated consolidation review at present.

No other workaround, unclear owner or interaction with unrelated conversion
subsystems was introduced or uncovered. The remaining constraints are the
explicit older-client bootstrap and native Windows validation. The next planned
extraction can proceed separately; v214 does not perform it.
